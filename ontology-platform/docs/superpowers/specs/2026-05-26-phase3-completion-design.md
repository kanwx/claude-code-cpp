## 1. DL/Tableaux ALC Reasoner

### Problem

The platform has no description logic reasoner. Complex OWL class reasoning (satisfiability, full subsumption, classification, realization) cannot be performed. The ClassExpressionEvaluator's TBox-aware overloads only handle structural decomposition — they cannot detect unsatisfiable classes like `Cat ⊓ ¬Cat`.

### Design

New `DlReasoner` class with TBox (terminological axioms) and ABox (assertional facts). Tableaux algorithm for ALC.

#### ALC Tableaux Algorithm

Input: concept expression C. Question: is C satisfiable?

1. Convert C to Negation Normal Form (push negations inward: ¬(A ⊓ B) → ¬A ⊔ ¬B, ¬∃R.C → ∀R.¬C, ¬∀R.C → ∃R.¬C)
2. Start with individual a: {a : C} plus any internalized TBox axioms
3. Apply Tableaux rules until saturated or clash detected:
   - **∧-rule**: If a : C ⊓ D, add a : C and a : D
   - **∨-rule**: If a : C ⊔ D, branch: add a : C OR a : D
   - **∃-rule**: If a : ∃R.C, generate fresh individual b, add (a,R,b) and b : C
   - **∀-rule**: If a : ∀R.C and (a,R,b) exists, add b : C
   - **¬-rule**: If a : ¬¬C, replace with a : C
4. **Clash**: individual has both C and ¬C (or ⊥)
5. **Blocking**: If individual b was generated by ∃-rule and has the same concept set as an ancestor, block (prevent further ∃-rule applications). Use subset blocking: block b if labels(b) ⊆ labels(ancestor).
6. **TBox internalization**: For each GCI C ⊑ D, add ⊤ ⊓ (C → D) = ⊤ ⊓ (¬C ⊔ D) to every individual's concept set.

#### Key Methods

| Method | Signature | Behavior |
|--------|-----------|----------|
| `addTBoxAxiom` | `(ClassExpression sub, ClassExpression sup)` | Add GCI |
| `addABoxAssertion` | `(String individual, ClassExpression concept)` | Add concept assertion |
| `addRoleAssertion` | `(String individual1, String property, String individual2)` | Add role assertion |
| `isSatisfiable` | `(ClassExpression concept) → bool` | Core Tableaux check |
| `isSubsumedBy` | `(ClassExpression A, ClassExpression B) → bool` | A ⊑ B iff A ⊓ ¬B unsatisfiable |
| `isEquivalent` | `(ClassExpression A, ClassExpression B) → bool` | A ≡ B iff A ⊑ B ∧ B ⊑ A |
| `isConsistent` | `() → bool` | Check whole ABox+TBox consistency |
| `classify` | `() → map<String, vector<String>>` | Compute full class hierarchy |
| `realize` | `(String individual) → vector<String>` | Find most specific types |

#### Integration with HybridReasoner

`HybridReasoner` gets an optional `DlReasoner*` member. When set:
- Consistency checks delegate to `DlReasoner::isConsistent()`
- Complex subsumption queries delegate to `DlReasoner::isSubsumedBy()`
- Falls back to existing TBox-aware ClassExpressionEvaluator when DlReasoner is not set

## 2. JSON-LD Writer + OWL/XML Writer Fix

### Problem

- `OntologyIO::writeRdf()` for JSON-LD format returns literal `"{}"`
- OWL/XML writer delegates to RDF/XML writer instead of producing native OWL/XML

### Design

#### JSON-LD Writer

Iterate TripleStore triples, group by subject, produce:

```json
{
  "@context": { "prefix1": "iri1", ... },
  "@graph": [
    {
      "@id": "subject1",
      "@type": "Class1",
      "predicate1": { "@id": "object1" },
      "predicate2": "literal_value"
    }
  ]
}
```

Logic:
1. Collect all prefixes from subjects/predicates/objects
2. Group triples by subject
3. For each subject: `@type` from rdf:type triples, other predicates as properties
4. Literal objects get `@value` + optional `@type`/`@language`
5. IRI objects get `@id`

#### OWL/XML Writer

Generate OWL 2 XML format:

```xml
<OwlXml:Ontology>
  <Declaration><Class IRI="C1"/></Declaration>
  <SubClassOf><Class IRI="C1"/><Class IRI="C2"/></SubClassOf>
  <ObjectPropertyDomain>
    <ObjectProperty IRI="p1"/><Class IRI="C1"/>
  </ObjectPropertyDomain>
</OwlXml:Ontology>
```

Map triples to OWL XML elements:
- `rdf:type owl:Class` → `<Declaration><Class/></Declaration>`
- `rdfs:subClassOf` → `<SubClassOf/>`
- `owl:disjointWith` → `<DisjointClasses/>`
- `rdfs:domain/rdfs:range` → `<ObjectPropertyDomain/>/<ObjectPropertyRange/>`
- `rdf:type` on individuals → `<ClassAssertion/>`
- Object property triples → `<ObjectPropertyAssertion/>`

- Modify: `src/io/OntologyIO.cpp` — fix both writers
- Create: `tests/test_io.cpp` — round-trip write+parse tests

## 3. AutoModel TBox-aware Enhancement

### Problem

- `detectConflicts()` uses hardcoded 3-pair mutex map (marriedTo/divorcedFrom, employedBy/firedFrom, alive/deceased)
- `alignEntities()` uses simple cosine similarity threshold (0.8)
- `mergeOntologies()` does basic merge without dedup or source tracking

### Design

#### Conflict Detection

Replace hardcoded mutex map with three strategies:

1. **Disjointness check**: Query TBox for `owl:disjointWith` (and its rdfs:subClassOf closure). If individual `a` is typed as both `C` and `D` where C and D are disjoint, flag conflict.
2. **Functional property violation**: Query for `owl:FunctionalProperty` declarations. If subject `s` has multiple values for functional property `p`, flag conflict.
3. **DlReasoner consistency**: If DlReasoner is available, call `isConsistent()` after each triple addition. Flag any inconsistency.

Conflicts reported as structured `Conflict` objects:
```cpp
struct Conflict {
    enum Type { DisjointClassAssertion, FunctionalPropertyViolation, Inconsistency };
    Type type;
    String description;
    std::vector<Triple> conflictingTriples;
    float severity;  // 0.0-1.0
};
```

#### Entity Alignment

Replace cosine-only with multi-signal alignment:

1. **Embedding similarity** (existing): cosine(vector(e1), vector(e2))
2. **Structural similarity**: Jaccard coefficient of shared properties/relations
3. **Label similarity**: normalized Levenshtein distance on class/entity names

Weighted combination: `score = w1*emb + w2*struct + w3*label` with configurable weights (default: 0.5, 0.3, 0.2).

Return top-N candidates per entity with confidence scores, not just above-threshold matches.

#### Knowledge Fusion

Replace basic merge with provenance-aware fusion:

1. **Provenance tracking**: Each triple gets a `source` field recording which ontology/document it came from
2. **Deduplication**: When merging, detect duplicate triples (same subject+predicate+object) across sources — keep one, record all sources in provenance
3. **Conflict resolution pipeline**: After merge, run enhanced `detectConflicts()`. For each conflict, apply resolution strategy (prefer higher-confidence source, or delegate to LLM).

Add `Provenance` struct:
```cpp
struct Provenance {
    String sourceId;       // ontology/document ID
    String sourceName;     // human-readable name
    float confidence;      // 0.0-1.0
    String timestamp;      // when this triple was added
};
```

Storage: provenance stored in a side map `unordered_map<size_t, Provenance>` keyed by triple hash.

#### Files

- Modify: `include/ontology/AutoModel.hpp` — add Conflict, Provenance structs; update method signatures
- Modify: `src/inference/AutoModel.cpp` — rewrite detectConflicts, alignEntities, mergeOntologies
- Modify: `tests/test_auto_model.cpp` — new tests

## 4. Temporal Reasoning (Allen Algebra)

### Problem

Only temporal *data* support exists (timestamps on triples, `isValidAt()`, `queryAtTime()`). No temporal *reasoning* — no interval relations, no temporal consistency checking, no temporal SWRL rules.

### Design

#### Allen Interval Algebra

13 relations between time intervals:

| Relation | Inverse | Meaning |
|----------|---------|---------|
| Before | After | A ends before B starts |
| Meets | MetBy | A end = B start |
| Overlaps | OverlappedBy | A starts before B, overlaps |
| During | Contains | A fully within B |
| Starts | StartedBy | A and B start together, A ends first |
| Finishes | FinishedBy | A and B end together, A starts later |
| Equals | Equals | Same interval |

Composition table: given R1(A,B) and R2(B,C), infer R3(A,C). Full 13×13 table (169 entries).

Implementation:
- `TemporalInterval` struct: `{start: String, end: String}` (ISO 8601 timestamps)
- `AllenRelation` enum: 13 values + `Unknown`
- `computeRelation(interval1, interval2) → AllenRelation` — compute from timestamps
- `compose(r1, r2) → set<AllenRelation>` — composition table lookup
- `inverse(r) → AllenRelation` — inverse relation lookup

#### Temporal Consistency Checking

1. **Path consistency algorithm**: For all triples of intervals (A,B), (B,C), compute (A,C) via composition. If result contradicts known (A,C), inconsistent.
2. **Functional property temporal check**: If `p` is functional and (a,p,b,t1) and (a,p,c,t2) exist, check that t1 and t2 don't overlap.
3. **Disjoint class temporal check**: If individual `a` is typed as `C` during [t1,t2] and `D` during [t3,t4] where C and D are disjoint, check that intervals don't overlap.

#### Temporal SWRL Rules

Extend SWRL engine to support temporal built-ins:
- `temporal:before(?t1, ?t2)` — t1 before t2
- `temporal:overlaps(?t1, ?t2)` — intervals overlap
- `temporal:during(?t1, ?t2)` — t1 during t2
- `temporal:contains(?t1, ?t2)` — t1 contains t2

These built-ins are evaluated against triple timestamps.

#### Bitemporal Support

Extend Triple struct with:
- `validFrom` / `validTo` — when the fact was true in the real world
- `recordedAt` — when the fact was recorded in the system

These are separate from the existing `confidence` field. Queries can target either time dimension.

#### Files

- Modify: `include/ontology/Temporal.hpp` — add AllenRelation, TemporalInterval, composition table, path consistency
- Modify: `src/inference/Temporal.cpp` (new file, extract from existing) — implement reasoning
- Modify: `include/ontology/Swrl.hpp` — add temporal built-ins to SwrlBuiltIns
- Modify: `src/swrl/Swrl.cpp` — implement temporal built-in evaluation

## 5. Distributed Storage (Single-node Simulation)

### Problem

No distributed storage support. All data is in a single in-memory TripleStore. Cannot scale beyond a single process.

### Design

Single-node simulation — all shards are separate TripleStore instances in the same process. No network RPC. Architecture is correct for future network transport addition.

#### Sharding

- **Shard key**: `hash(subject) % numShards` — all triples for a given subject land in the same shard
- Each shard is an independent `TripleStore` instance
- `ShardManager` routes operations to the correct shard(s):
  - Subject-keyed operations (findBySubject, findBySP): single shard
  - Predicate-only (findByPredicate, findByPO): fan-out to all shards, merge results
  - Full scan (getAllTriples, count): fan-out to all shards, aggregate

#### Replication

- Each shard has a primary + N replicas (configurable, default 2 replicas = 3 copies)
- Primary handles writes, replicates to all replicas synchronously
- Reads can go to any replica (round-robin load balancing)
- Quorum writes: majority of replicas must acknowledge (2 of 3 default)
- Replica states: `LEADER`, `FOLLOWER`, `CATCHING_UP`

#### Consistency

- **Read-after-write consistency**: writes go to leader, reads from leader after write
- **Eventual consistency**: reads from followers may be slightly behind
- **Vector clocks**: each triple gets a version vector `{shardId: counter}` for conflict detection
- **Conflict resolution**: last-write-wins (based on vector clock comparison) + application-level merge

#### Cluster Configuration

```cpp
struct ClusterConfig {
    int numShards = 4;
    int replicationFactor = 3;
    bool readFromFollowers = true;  // allow follower reads
    int writeQuorum = 2;            // majority
};

struct ClusterHealth {
    int totalShards;
    int healthyShards;
    int totalReplicas;
    int healthyReplicas;
    bool allShardsAvailable;
};
```

#### Interface

`DistributedStorage` implements the same public interface as `HybridStorage` (addTriple, removeTriple, findBySubject, etc.). It can be used as a drop-in replacement.

Additional methods:
- `getClusterHealth() → ClusterHealth`
- `getShardInfo(shardId) → ShardInfo`
- `rebalance()` — redistribute triples across shards
